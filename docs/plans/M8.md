# M8: speed

Read first: `docs/STATE.md`, `docs/research.md` (speed rules), `docs/research/speed-astra-2026-10-23.md` (the 15 ranked changes), `docs/decisions.md` (V1 and what reopens it), `docs/design-spec.md` section 7, and the bench scripts in `bench/`.

Done-test (all medians of 5, Release build, Developer ID signed, on this Mac):
1. Launch to keystroke-ready at least 25 ms under TextEdit's window-visible median (TextEdit 265.2 ms, so QuickEdit at most 240 ms), measured by `bench/run-bench.sh` with both apps interleaved. Needs an unlocked screen.
2. Typing: p50 at most 1.5 frames + 3 ms and p95 at most 2 frames + 3 ms on a 1 MB file (60 Hz display: p50 <= 28 ms, p95 <= 36.3 ms). Needs an unlocked screen.
3. 100 MB short-line file: usable (window shows text and accepts a keystroke) in under 1 s from the open request. 10 MB: under 250 ms.
4. 1 GB file: no spinning wheel. If it cannot be edited in memory on this 8 GiB Mac, it opens in a limited mode that says so (see n4).
5. Wrap to Page on 10 MB: no main-thread stall over 100 ms after the switch (M5 measured 340 ms).
6. The TextKit 1 vs TextKit 2 benchmark that can reopen vote V1 is run and recorded (done 2026-10-24).
7. Export as PDF of a 10 MB file keeps the window responsive (no main-thread block over 100 ms) and can be cancelled.
Time budget: 6 hours.
Not in this version: a custom text engine.

## Measurement first (root runs all timing; builders add the hooks)
- `os_signpost` intervals at: main start, menu built, first window created, document read start/end, decode end, storage installed, first layout, first key accepted. Builders add these with an `OSSignposter` (category `QuickEdit`), compiled in Release; their cost must be under 0.1 ms total at launch.
- `bench/openbench.swift`: opens a fixture via `-QEOpenPath`, waits for the ready stamp, records the time; interleaved n=5 against TextEdit opening the same file through `open -a TextEdit <file>` with window-visible timing.
- `bench/typetest`: port Fastpad's `bench/typetest.sh` and `bench/tools/drive.swift` (real HID key events, ready stamps from the app on each text change, display-frame timing).
- Instruments recording is not available from the shell (`xctrace` lists no instruments); use signposts plus the harness.

## Nodes

### n1: launch path
difficulty: hard
owns: QuickEdit/App/*, QuickEdit/Support/*, project.yml
steps:
  1. Measure the launch phases with signposts; list every piece of work before the first window.
  2. Remove or defer anything not needed for the first window (encodings list, Settings, panels, recent-documents work, spelling setup if deferrable, restoration of nothing).
  3. Build settings: compare `-O` vs `-Osize`, LTO on vs off, dead stripping; keep the fastest launch. Report a table.
     verify: root's `bench/run-bench.sh 5` table before and after

### n2: open path
difficulty: hard
owns: QuickEdit/Document/*, QuickEdit/Window/DocumentWindowController.swift, QuickEdit/Window/TextViewFactory.swift
steps:
  1. Read with `Data(contentsOf:options: .mappedIfSafe)`; decode off the main thread (already concurrent); fill the storage before the layout manager attaches; avoid any extra full copy of the text (count copies with signposts and memory peaks).
  2. For files over a size limit (start at 50 MB, tune by measurement), turn off spelling, grammar, data detectors and substitutions for that window, and say so in the window (a small banner or the title suffix, decided with Astra and Fable if unclear).
     verify: `bench/openbench` for 1 MB, 10 MB, 100 MB, long-line 10 MB; peak memory (`/usr/bin/time -l` or task_info) for each

### n3: Wrap to Page stall
difficulty: hard
owns: QuickEdit/Window/DocumentWindowController.swift, QuickEdit/Window/MultiplePageView.swift
steps:
  1. Remove the 340 ms stall after switching a 10 MB document to Wrap to Page: e.g. generate glyphs in slices on idle (`ensureGlyphs(forCharacterRange:)` in chunks between run-loop turns) so no single main-thread block exceeds 50 ms, or another approach that keeps the shared layout manager design. If no approach works, report the measurements before choosing.
     verify: a unit test records main-thread gaps over the 3 s after the switch; max under 100 ms (optimized)

### n4: very large files
difficulty: hard
owns: QuickEdit/Document/LargeFile*.swift, QuickEdit/Window/LargeFileWindowController.swift (if needed)
steps:
  1. Measure the 1 GB fixture: time and peak memory to open in the normal path, on this 8 GiB Mac.
  2. If it cannot open in under 5 s without memory pressure, add a limited mode for files above a threshold: read-only view of the file through a memory-mapped line index (no full decode), with a clear title note ("Read only: file too large to edit") and Find working on the mapped bytes. Ask Astra and Fable before building this mode (root runs the vote with the measurements).
     verify: 1 GB fixture opens with no stall over 200 ms on the main thread; memory stays under 1.5 GB

### n6: PDF output on large files (from M7 review row 14 and M7 follow-ups)
difficulty: medium
owns: QuickEdit/Document/PDFRenderer.swift, QuickEdit/Document/TextDocument.swift (PDF parts only), QuickEditTests/PrintTests.swift
steps:
  1. Measure Export as PDF on 1 MB, 10 MB and 100 MB in both view modes: time, longest main-thread block, peak memory. Today 1 MB blocks the main thread 0.5 to 0.9 s in one piece.
  2. Keep the window responsive: lay out and draw off the main thread from a copy of the text (the renderer already draws from a copy), with a progress sheet and a working Cancel for anything over 1 s; no main-thread block over 100 ms. Memory stays under 2x the file's in-memory text size.
     verify: unit tests record main-thread gaps during a 10 MB export (max under 100 ms) and that Cancel leaves no file and no temp folder

### n7: typing p95 on 100 MB
difficulty: medium
owns: QuickEdit/Window/TextViewFactory.swift, QuickEdit/Window/DocumentWindowController.swift (typing path only)
steps:
  1. The TextKit 2 benchmark (docs/decisions.md, V1 check) measured TextKit 1 typing p95 at 14.3 ms on the 100 MB file (TextKit 2: 1.7 ms). Find where the time goes (signposts in the typing path: encoding check, line-ending handling, layout invalidation) and cut it, staying on TextKit 1.
     verify: root's typing harness on the 100 MB file, p95 at most 8 ms

### n5: TextKit 2 comparison (DONE 2026-10-24: TextKit 1 stays; see docs/decisions.md, V1 check)
difficulty: medium
owns: bench/tk2bench.swift
steps:
  1. A standalone Release benchmark: NSTextView on TextKit 2 vs TextKit 1 with non-contiguous layout; 100 MB short lines and 10 MB one paragraph; open time, jump to end time, p95 typing time at the end, peak memory. n=5 each.
     verify: a table in the report; root records it in `docs/decisions.md`

## Hands-on script for the user
1. Launch QuickEdit and TextEdit side by side from the Dock: QuickEdit's window should appear first.
2. Open `bench/fixtures/100mb.txt` in both.
3. Type fast in a 1 MB file.
4. Taste question: does it feel faster?
