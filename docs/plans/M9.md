# M9: system parts, custom shortcuts, sandbox on

Read first: `docs/STATE.md`, `docs/design-spec.md` (sections 1, 3 and 8), `docs/codemap.md` (Services and drag rows), `docs/parity.md` rows P71 to P73, `docs/decisions.md` (U2, U3), and `docs/plans/M1.md` (the 12 builder rules).

Tier 3: the App Sandbox changes which files the app may read and write, and it moves the saved settings into a new folder. So M9 gets full tests, two reviews and a diagram.

Done-test:
1. An accessibility audit (`XCUIApplication.performAccessibilityAudit()`, the test version of Accessibility Inspector's audit) of the document window, the Settings window (every tab) and the Select Line panel has no errors.
2. A changed shortcut works at once, works again after a relaunch, and a clash with another command is refused with a message.
3. The Release build is signed with the App Sandbox on, and `codesign -d --entitlements -` shows exactly `com.apple.security.app-sandbox` and `com.apple.security.files.user-selected.read-write`.
4. `./build.sh test` passes in full with the sandbox on (the sandbox is on in the Debug build that the tests use, too).
5. Settings that the user saved before M9 are still there after the first sandboxed launch.

Time budget: 5 hours. n1 1.5 h, n2 1 h, n3 2 h, reviews and release 0.5 h.

Not in this version: AppleScript and QuickEdit's own Services (U3); a Quick Look extension of our own (macOS already previews `.txt`); shortcuts for items in the system-made menus (Services, Writing Tools, Window list); importing or exporting a shortcut set.

## Order
UI tests take over the screen, so only one builder runs them at a time. n1 goes first, because the sandbox changes how every test opens files. The Keyboard tab mockups and their vote run while n1 builds. n2 and n3 then go to one builder, because both change `MainMenu.swift`.

## Nodes

### n1: App Sandbox on
difficulty: hard
owns: QuickEdit/Resources/QuickEdit.entitlements, QuickEdit/Resources/Info.plist, QuickEdit/Resources/container-migration.plist (new), project.yml, build.sh, QuickEditUITests/UITestSupport.swift, QuickEditTests/SandboxTests.swift (new), QuickEditUITests/SandboxUITests.swift (new), and the smallest fix in any file a sandbox failure points at (list each one)
steps:
  1. Turn the sandbox on with only `com.apple.security.files.user-selected.read-write`, in Debug and Release. Run the full suite once and list every failure with its cause before fixing anything.
  2. Tests: fix how tests reach their fixtures. Prefer fixtures inside a folder the sandboxed app may use (its container, or files the test hands over through `-QEOpenPath` after the runner copies them in). If no such route works, a Debug-only entitlement that names the fixture folder is allowed; Release must never carry it. Ask root before anything wider. A shell test checks the Release entitlements are exactly the two keys (done-test 3).
  3. Settings move: add `container-migration.plist` so `~/Library/Preferences/dev.yili.QuickEdit.plist` moves into the container on first launch (done-test 5). Test it with a scratch bundle-ID copy, never with the user's real settings file.
  4. Re-check each file path under the sandbox with a test: open, save, Save As with a changed extension (`NSIsRelatedItemType` for `.txt` and no extension if needed), autosave and Versions, Revert, Reopen with Encoding, Open Recent after relaunch, window restoration, the large-file clone (V3) and its Save As, Export as PDF, the outside-change reload, and the `-QETestExternalWrite` hook.
     verify: `./build.sh test` in full; `codesign -d --entitlements -` on the Release app

### n2: system parts
difficulty: medium
owns: QuickEdit/App/MainMenu.swift (Share and Services items only), QuickEdit/Window/TextViewFactory.swift, QuickEdit/Window/DocumentWindowController.swift (drag and accessibility parts only), QuickEditTests/SystemPartsTests.swift (new), QuickEditUITests/AccessibilityAuditTests.swift (new)
steps:
  1. Drag and drop (P72): a file dropped on the Dock icon or the window's title bar opens it; text dragged in or out of the text view is plain text only; a file dropped into the text inserts its path, as TextEdit's plain mode does.
  2. Share (P73): File > Share submenu built from `NSSharingService` for the document's file; disabled for an unsaved document.
  3. Writing Tools (P73): on for the text view with plain-text results only; off in read-only large-file mode.
  4. Services (P71): the system Services menu works with the selection (send and receive plain text).
  5. Accessibility: run the audit from done-test 1 and fix every error (labels, roles, contrast, hit targets). Full keyboard access reaches every control in Settings and the Select Line panel.
  6. Quick Look: a test runs `qlmanage -t` on a file QuickEdit saved and checks a thumbnail is made.
     verify: `./build.sh only` for the new tests, then `./build.sh test`

### n3: custom keyboard shortcuts (U2)
difficulty: hard
owns: QuickEdit/Support/Shortcuts.swift (new), QuickEdit/App/MainMenu.swift, QuickEdit/Window/SettingsWindowController.swift (new Keyboard tab), QuickEdit/Window/ShortcutRecorder.swift (new), QuickEdit/Support/Defaults.swift, QuickEditTests/ShortcutTests.swift (new), QuickEditUITests/ShortcutUITests.swift (new)
steps:
  1. Give every menu command QuickEdit builds a stable id. Store changes only (id to key and modifiers) under one new defaults key; the default set stays in code.
  2. A Keyboard tab in Settings, laid out as mockup A, one flat table with a header row per menu (user decision U4 in `docs/decisions.md`, with the changes listed there): each command, its shortcut, click to record a new one, a reset per row, and Restore Keyboard Defaults.
  3. A clash with another command, or a key the system keeps (Cmd+Tab, Cmd+Space, Cmd+Option+Esc), is refused with a message that names the other command. A shortcut needs Cmd or Ctrl, except function keys.
  4. A change applies to the menu at once, with no relaunch. Shortcuts the user set in System Settings (App Shortcuts) still win, as AppKit does by default; the tab says so.
     verify: unit tests for store, clash and apply; a UI test that changes a shortcut, uses it, relaunches and uses it again (done-test 2)

## Acceptance (root checks)
1. Every done-test, with its evidence recorded in `docs/STATE.md`.
2. `./build.sh test` in full on the merged dev branch, plus `./build.sh speed` (the sandbox may change file speed).
3. Astra and a fresh Opus reviewer read the change; findings in `docs/reviews/M9-code.md`.
4. Diagram `docs/diagrams/M9.html` (what the sandbox lets through).
5. `./build.sh dist M9`, GitHub release m9.

## Hands-on script for the user
1. Open a `.txt` from Finder, edit, save, close, reopen it from Open Recent.
2. Settings > Keyboard: change New to Cmd+Shift+Y, use it, quit, relaunch, use it again.
3. Try to give Save the same shortcut as Open: it should be refused.
4. Select text, then Edit > Writing Tools, and File > Share.
5. Turn on VoiceOver (Cmd+F5) and read a line.
