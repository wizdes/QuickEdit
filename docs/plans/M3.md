# M3: encodings and line endings

Read first: `docs/STATE.md`, `docs/design-spec.md`, `docs/parity.md` rows P20 to P29, `docs/codemap.md` sections 1.11 (EncodingManager), 3 (defaults `PlainTextEncoding`, `PlainTextEncodingForWrite`, `Encodings`) and 4 (the whole open and save path), and `reference/apple/EncodingManager.m`, `reference/apple/Document.m:160-307` and `:950-1139`, `:1266-1321`.

Done-test: about 30 fixture files in different encodings open, save and come back byte-for-byte equal, and QuickEdit's "Automatic" guess for each matches AppKit's plain-text reader (the engine system TextEdit uses).
Time budget: 4 hours.
Not in this version: the Settings window controls for the two encoding defaults (M6; the defaults themselves work now), rich-text detection (never).

## Key idea: AppKit is the oracle
TextEdit has no detection code; AppKit's plain-text reader decides (codemap 4.2). So the test oracle is AppKit itself: for each fixture, `NSAttributedString(url:options:[.documentType: .plain], documentAttributes:)` gives the encoding AppKit picks (`.characterEncoding` document attribute). QuickEdit decodes on its own (no attributed-string reader in the app's open path, it is slow and hides decoding) but must agree with that oracle on every fixture, or the disagreement is listed in the report with the reason and root decides.

## Nodes

### n1: decoding and encoding
difficulty: hard
owns: QuickEdit/Document/PlainTextIO.swift, QuickEditTests/EncodingTests.swift, QuickEditTests/Fixtures/encodings/ (generated by a script in the same folder)
steps:
  1. `PlainTextIO.decode(_ data: Data, url: URL?, preferred: String.Encoding?)`:
     - `preferred` (an explicit choice from the Open panel or the `PlainTextEncoding` default) wins; if the bytes do not fit, throw `inapplicableEncoding(name)`.
     - Else, in order: the `com.apple.TextEncoding` extended attribute of `url` (format `<IANA name>;<CFStringEncoding number>`; use the number), a BOM (UTF-8, UTF-16 LE/BE, UTF-32 LE/BE), strict UTF-8, then `NSString.stringEncoding(for:encodingOptions:convertedString:usedLossyConversion:)` with `.allowLossyKey: false` and suggested encodings from the `Encodings` list, then the fallback AppKit uses (find it with the oracle; report which).
     - The result records the encoding, BOM, dominant line ending, and `lossy: Bool`.
     - Reading stays off the main thread and stays one pass over the bytes where possible: never decode the whole file more than twice.
  2. `encode` writes the chosen encoding, keeps a BOM exactly when the file had one (UTF-16 without a BOM gets a BOM, as AppKit does; check with the oracle), never converts line endings.
  3. A fixture generator writes about 30 files: UTF-8 (with and without BOM), UTF-16 LE/BE with BOM, UTF-32, Mac Roman, Windows-1252, ISO Latin 1, Shift JIS, EUC-JP, GB 18030, Big5, KOI8-R, Windows-1251, ISO-8859-7, pure ASCII, empty, one with an xattr naming Windows-1252 over bytes that are also valid UTF-8, one invalid in every guessed encoding, CR, LF, CRLF and mixed endings.
     verify: `./build.sh unit` runs `EncodingTests`: for each fixture, guess == oracle (or listed exception), and open -> save -> bytes identical. Count printed.

### n2: Open and Save panels, encodings list
difficulty: medium
owns: QuickEdit/Document/EncodingManager.swift, QuickEdit/Document/DocumentController.swift, QuickEdit/Document/TextDocument.swift
steps:
  1. `EncodingManager`: the encodings list (`Encodings` default; first-run list = TextEdit's default list from `reference/apple/EncodingManager.m`), a pop-up builder (with or without "Automatic"), and the "Customize Encodings List…" panel built in code (an `NSTableView` with a checkbox column, Select All, Revert to Default). Created on first use only.
  2. Open panel accessory: "Plain Text Encoding:" pop-up with Automatic first, starting at the `PlainTextEncoding` default; the choice applies to the URLs opened from that panel only (TextEdit's `customOpenSettings`, without locks: hand the choice to the document through the controller on the main thread).
  3. Save panel: the encoding pop-up next to the ".txt" checkbox, starting at the document's encoding if the text fits, else UTF-8 (or `PlainTextEncodingForWrite` if it fits). Items whose encoding cannot hold the text are disabled; skip that check when items x characters >= 5,000,000 (TextEdit's limit). After a good Save or Save As the chosen encoding becomes the document's encoding. Autosave always uses the document's encoding.
  4. Write the `com.apple.TextEncoding` xattr on save (`<IANA name>;<CFStringEncoding>`), as AppKit does for TextEdit.
     verify: unit tests for the pop-up contents and disabled items; UI tests for the Open panel choice and Save panel encoding change (NOT RUN if the screen is locked); a unit test reads the xattr after save

### n3: alerts and line endings
difficulty: medium
owns: QuickEdit/Document/TextDocument.swift, QuickEdit/Window/DocumentWindowController.swift
steps:
  1. Encoding no longer fits (P25): after each user edit, check only the inserted characters (not the whole document) against the document's encoding. On the first failure show TextEdit's sheet ("This document can no longer be saved using its original %@ encoding." / "Please choose another encoding (such as UTF-8)."), OK opens the Save panel, Cancel undoes the edit. Use closures, not the selector and `objc_msgSend` recovery TextEdit uses. Skip for untitled documents (as TextEdit).
  2. Lossy load (P26): before writing over a file that loaded lossily, show "Are you sure you want to modify the document in place?" with Duplicate, Cancel, Overwrite.
  3. Line endings (P27, better than TextEdit): Return and Enter insert the document's dominant line ending (LF for new documents). Paste keeps pasted text as is.
     verify: unit tests drive the text view (`insertText`, `insertNewline`) and check the storage; the alert paths are tested by calling the check functions with a fake presenter

## Speed checks (root)

## Acceptance (root checks)

2. `./build.sh test` passes or UI tests are reported NOT RUN.
3. P20 to P29 updated in `docs/parity.md`.

## Hands-on script for the user
1. File > Open, pick a Windows or Mac Roman .txt file with "Automatic": accented letters look right.
2. Type an emoji into that file and save: the "can no longer be saved" sheet appears.
3. Save As with a different encoding from the pop-up, reopen: the text is the same.
4. Open a Windows (CRLF) file, press Return, save: the file stays CRLF only (`cat -v` shows `^M` on every line).
