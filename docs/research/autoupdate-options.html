How should QuickEdit update itself?

I compared 8 ways for a Mac app to get new versions to its users. QuickEdit runs in the App Sandbox and may not use the network. Only Sparkle is built for that.

Pick one: Sparkle 2, a "new version" notice only, or the Mac App Store.
My pick
Sparkle 2.10.1. It is the standard open source updater for Mac apps (MIT license). It works in a sandboxed app through two small helper processes that ship inside it. QuickEdit can keep its network block, because Sparkle's helper does the download.
Lighter choice
Notice only. QuickEdit checks GitHub once a day and shows "QuickEdit 1.3 is out" with a Download button. You still drag the new app in by hand. This needs one new sandbox permission: network access.
After you pick
I write a short build plan for your OK. Adding Sparkle is Tier 3 work: it changes signing and the sandbox permissions, and it needs a new signing key in ~/keys. I will ask before I make that key.

The sandbox is the deciding fact. A sandboxed app can't overwrite its own copy in /Applications. Every GitHub-only updater I found replaces the app from inside the running app, so none of them work here.

How Sparkle would work in QuickEdit

The sandbox needs one more permission line for this: a lookup exception for the names dev.yili.QuickEdit-spks and dev.yili.QuickEdit-spki. Both Info.plist switches go on: SUEnableInstallerLauncherService and SUEnableDownloaderService.

Each option in detail

Sparkle 2

Works with the sandbox on

Most Mac apps sold outside the App Store use this. You publish a small feed file (the appcast) that lists versions. Sparkle reads it and shows the standard update window with release notes.

Good

  • Built for sandboxed apps; QuickEdit keeps its network block.
  • Each update is signed with your own EdDSA key, so a hacked GitHub account alone can't push a bad update.
  • Swaps the app when you quit; you are never cut off mid-edit.
  • generate_appcast builds the feed and the signatures from a folder of DMGs.
  • Active: release 2.10.1 came out 3 days ago.

Costs

  • Adds 2.9 MB to an app whose DMG is 2.3 MB today.
  • One new sandbox permission line, so the sandbox test changes.
  • A new private key to keep in ~/keys. If it is lost, old copies can't take updates.
  • The XPC helpers must be signed by hand in build.sh. Sparkle's docs warn against codesign --deep.

Notice only

Needs network permission

QuickEdit asks the GitHub releases API once a day. When a newer tag exists, it shows a small window with a Download button that opens the release page. Nothing is installed for you.

Good

  • No library, no new key, no new host.
  • Can't break the installed app, because it never touches it.

Costs

  • Adds the network.client permission. A text editor that can reach the network is a bigger change to explain than Sparkle's helper.
  • You still download, open the DMG and drag. That is the step people skip.
  • GitHub allows 60 unauthenticated API calls an hour per IP address.

Mac App Store

Updates come from macOS

QuickEdit is already sandboxed, which the App Store requires. Apple ships updates the same way as for every other store app.

Good

  • No updater code at all.
  • Users find it in the store.

Costs

  • Each release waits for App Review.
  • A second release process beside the DMG, or a full move.
  • Not a library choice; a distribution choice.

Homebrew cask in your own tap

Only for brew users

A small Ruby file in a wizdes/homebrew-tap repo points at the DMG. People who install with brew install --cask get updates with brew upgrade.

Good

  • No change to the app.
  • Pairs well with any other choice here.

Costs

  • Helps only people who use Homebrew.
  • One more file to update at each release.

mxcl/AppUpdater

Not with the sandbox on

A small Swift package that reads GitHub Releases, checks a DMG and replaces the running app. Its checks are strict: Developer ID, same Team ID, same bundle ID. QuickEdit's DMG name already fits its rule (QuickEdit-1.2.1.dmg).

Good

  • No feed and no extra key; GitHub Releases is the feed.
  • Optional proof that the DMG came from a GitHub Actions build.

Costs

  • Replaces the app from inside the running process. The sandbox blocks that, and the README doesn't mention sandboxed apps.
  • The build proof needs GitHub Actions; QuickEdit builds on this Mac.
  • No update window; you build that yourself.

s1ntoneli/AppUpdater

Not with the sandbox on

A rewrite of mxcl's package with async/await and a SwiftUI settings view. Its README says: "Only non-sandboxed apps are supported."

One-file updater

Not with the sandbox on

Flavio Copes describes a 436-line Swift file with no dependencies. It checks GitHub daily, compares SHA-256 with GitHub's digest, checks the code signature, swaps the app and relaunches. His post says it is "for apps that aren't sandboxed".

Squirrel.Mac

Not a fit

The updater inside Electron. Its last release is 0.3.2 from 2017, and it expects a server that answers "is there an update" requests.

If you pick Sparkle, the work looks like this

  1. Add Sparkle 2.10.1 as a Swift package and add "Check for Updates…" to the QuickEdit menu.
  2. Turn on both helpers in Info.plist, and add the one sandbox lookup line. Update the sandbox test to expect it.
  3. Sign the two helpers in build.sh before the app is notarized.
  4. Make the EdDSA key with Sparkle's generate_keys (I ask you first) and save it in ~/keys.
  5. Add generate_appcast to the release recipe and host appcast.xml next to the DMG.
  6. Ship 1.3 with the updater. People on 1.2.1 install that one by hand; every later version updates itself.
